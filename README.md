# PulseSearch

**A real-time document search engine.** Upload PDFs and text files, watch them get
processed live, then search them by **keyword**, by **meaning**, or with a **hybrid** of
both. Results are re-ordered by a cross-encoder, and you can optionally ask questions in
plain English and get an AI answer that cites your documents.

PulseSearch is a portfolio project. It aims to show production-quality engineering
rather than a demo: a layered backend, real async background processing, real keyword
and vector search, caching, rate limiting, retries with idempotency, metrics, and a test
suite that runs against a real Postgres and Redis. Everything runs from one
`docker compose up`.

## Features

| Area | What you get |
|---|---|
| **Accounts** | Register, log in, JWT auth, bcrypt password hashing, forgot/reset-password flow by email |
| **Uploads** | PDF, `.txt` and `.md` up to 20 MB (configurable). The API responds `202 Accepted` right away, and processing happens in the background |
| **Live processing** | Each document moves through `UPLOADED → PROCESSING → TEXT_EXTRACTED → INDEXING → GENERATING_EMBEDDING → COMPLETED` (or `FAILED`), streamed to the browser over Server-Sent Events. No polling |
| **Keyword search** | PostgreSQL full-text search (`tsvector` + GIN index, ranked with `ts_rank_cd`) |
| **Semantic search** | Local `all-MiniLM-L6-v2` embeddings (384-dim), cosine similarity through pgvector with an IVFFlat index |
| **Hybrid search** | Normalized keyword score and semantic score blended with configurable weights (default 0.6 / 0.4) |
| **Reranking** | A cross-encoder (`ms-marco-MiniLM-L-6-v2`) re-scores the top candidates and drops results that aren't actually relevant |
| **AI Q&A** *(optional)* | Ask a question and get an answer generated by Claude from your own documents, with citations. Off by default because each call costs money |
| **Demo data** | Every new account gets 3 real documents run through the real pipeline, so the app isn't empty on first login |
| **Analytics** | Search volume, mode breakdown, zero-result queries, average latency, documents by status |
| **Caching** | Search results (60 s) and AI answers (5 min) cached per user in Redis |
| **Rate limiting** | Per-user fixed-window limits on search, upload, ask and password reset, stored in Redis |
| **Pluggable providers** | You can swap storage (local disk or S3/MinIO), embeddings (local or any OpenAI-compatible API), and email (console or SMTP) through config alone |
| **Observability** | Prometheus metrics for the API and the worker, request IDs, structured logs, a health check |
| **Ops** | Docker Compose stack, Alembic migrations, GitHub Actions CI, optional read-replica routing |

## How it works

### Architecture

```
                         ┌──────────────────────────┐
                         │   Next.js frontend :3000 │
                         │  (App Router, TanStack Q) │
                         └────────────┬─────────────┘
                                      │ HTTP (JSON) + SSE
                                      ▼
┌───────────────────────────────────────────────────────────────────┐
│                       FastAPI API  :8000                          │
│  routes → services → repositories      middleware: CORS,          │
│  auth · documents · search · ask       request-ID, metrics        │
│  events (SSE) · jobs · analytics       rate limiting (Redis)      │
│  health · /metrics                     embedding + reranker models│
└──────┬──────────────────────┬───────────────────────┬─────────────┘
       │ SQL (async)          │ cache / queue /       │ file bytes
       ▼                      ▼ pub-sub               ▼
┌──────────────────┐   ┌──────────────┐        ┌──────────────────┐
│ PostgreSQL 16    │   │   Redis 7    │        │ Storage          │
│ + pgvector       │   │ cache        │        │ local disk or S3 │
│ users, documents │   │ arq queue    │        └────────▲─────────┘
│ chunks (tsv+vec) │   │ pub/sub      │                 │
│ jobs, events     │   │ rate limits  │                 │
└────────▲─────────┘   └──────┬───────┘                 │
         │                    │ jobs                    │
         │             ┌──────▼──────────────────────┐  │
         └─────────────┤  arq worker   (metrics:9100)├──┘
                       │ extract → chunk → embed →   │
                       │ index → publish status      │
                       └─────────────────────────────┘
```

The backend uses a strict layering:

- **`api/routes`** handle HTTP concerns only: validation, auth dependencies, status codes.
- **`services`** hold business logic: search, processing, ask, auth, caching, the event bus.
- **`repositories`** are the only place SQL is written.
- **Provider interfaces** (`EmbeddingProvider`, `RerankerProvider`, `StorageProvider`,
  `EmailProvider`, `AIAnswerProvider`) sit behind small factories, so implementations
  are chosen from config and replaced with stubs in tests.

The full diagram, request flows and the reasoning behind each component are in
[`docs/architecture.md`](docs/architecture.md).

### Document processing pipeline

1. **Upload** (`POST /api/documents`). The API checks the extension, size and content
   (a `.pdf` must start with the `%PDF-` magic bytes), saves the file to storage, creates
   a `documents` row (`UPLOADED`) and a `processing_jobs` row, enqueues an arq job, and
   returns `202` with the document and job IDs. Processing never blocks the request.
2. **Worker picks up the job** and runs `ProcessingService.process()`:
   - **Text extraction**: `pypdf` for PDFs, UTF-8 decoding for text and Markdown, then
     whitespace normalization. Status becomes `PROCESSING`, then `TEXT_EXTRACTED`.
   - **Chunking** (`INDEXING`): sentence-aware chunks of up to **220 words** with a
     **40-word overlap**. Chunks are packed to whole sentences, so snippets read
     naturally. Text with no punctuation, or a single very long sentence, falls back to
     fixed word windows, so no content is ever dropped.
   - **Embedding** (`GENERATING_EMBEDDING`): all chunks are embedded in one batch.
   - **Indexing**: chunks are stored with their `tsvector` (generated by Postgres) and
     `vector(384)` embedding.
   - Status becomes `COMPLETED`.
3. **Each status change** is written to Postgres and published on Redis pub/sub, so open
   browsers update immediately.

Both the API and the worker **warm their models at startup**, and the embedding model is
**baked into the Docker image** at build time. Without that, the first request after a
fresh start would pay a cold model load, which can take anywhere from seconds to more
than a minute. See [`docs/performance.md`](docs/performance.md) for the bugs this fixed.

### Search modes and ranking

`GET /api/search?q=...&mode=keyword|semantic|hybrid`

| Mode | How it scores | Best for |
|---|---|---|
| `keyword` | `ts_rank_cd` over the chunk's `tsvector` (GIN index) | Exact terms, names, error codes |
| `semantic` | Cosine similarity between the query embedding and chunk embeddings (pgvector, IVFFlat) | Paraphrased or conceptual queries ("make the API faster" finds "reduce latency") |
| `hybrid` *(default)* | `0.6 × normalized_keyword + 0.4 × semantic` | General use |

**How hybrid works.** It fetches 3× the page size from both keyword and semantic search,
min-max normalizes the keyword scores (since `ts_rank_cd` has no upper bound), merges
the two lists by document, blends the scores, and sorts.

**Reranking** (enabled by default). The top `RERANK_CANDIDATE_POOL` candidates (default
10) from any mode are re-scored by a cross-encoder, which reads the query and each
snippet together. That is slower but much more accurate than comparing embeddings.
Candidates scoring below `RERANK_MIN_SCORE` (default `0.0`) are **dropped**. In measured
tests, relevant hits scored +3 to +6 and irrelevant ones −9 to −11. This filter is why a
query with no real matches returns nothing instead of the "least bad" documents. If the
reranker fails, search falls back to retrieval order instead of erroring.

Each response includes the per-signal scores (`keyword_score`, `semantic_score`,
`rerank_score`), `matched_terms` and `latency_ms`, so you can see why a result ranked
where it did. Every search is logged to `search_events` for analytics, and results are
cached in Redis per user, query, mode and page.

### AI Q&A (retrieval-augmented generation)

`GET /api/ask?q=What does the worker do when a job fails?`

1. Runs the **same hybrid + rerank + relevance-floor pipeline** as search and takes the
   top `AI_ANSWERS_CONTEXT_CHUNKS` (default 5).
2. **If nothing relevant is found, the model is never called.** The API returns
   "I couldn't find anything in your documents about that." This means no hallucinated
   answers and no cost for empty questions.
3. Otherwise, it sends the question and the context chunks to Claude (Anthropic SDK)
   and returns `{ question, answer, citations[] }`.

It is **off by default**. Set `AI_ANSWERS_ENABLED=true` and `ANTHROPIC_API_KEY` to turn
it on. While it is disabled the endpoint returns a clear `503`, and an upstream model
error returns `502`. Answers are cached for 5 minutes and limited to 10 requests per
minute per user.

### Real-time updates

There are two SSE streams, both backed by Redis pub/sub:

- **`GET /api/documents/{id}/events`**: one document's status. It sends the current
  status first, then each transition, and closes on `COMPLETED` or `FAILED`.
- **`GET /api/events`**: a per-user activity feed covering every document transition and
  every search. This is what keeps the dashboard counters live without refreshing.

The browser's `EventSource` can't send an `Authorization` header, so the SSE endpoints
also accept the JWT as `?token=...`.

### Reliability: retries, idempotency, failure handling

- **Retries with exponential backoff.** A failed job is retried with a delay of
  `min(60, 2^attempt)` seconds, up to `JOB_MAX_RETRIES`. Attempt count and last error
  are stored in Postgres (`processing_jobs`), not just in arq, so they survive restarts
  and can be read through `GET /api/jobs/{id}`.
- **Idempotent processing.** Re-running the pipeline for a document deletes and
  re-inserts its chunks in one transaction and overwrites its status and text. A retried
  job ends in the same state instead of creating duplicate chunks.
- **Permanent failures** set the document to `FAILED` with an `error_message` that the UI
  shows.
- **The rate limiter fails open.** If Redis has a problem, requests are allowed (with a
  warning logged) rather than taking the API down.
- **Unhandled exceptions** return a generic `500` with a short `error_id` that matches
  the logged stack trace. Internals are never leaked to the client.
- **Health check.** `GET /api/health` reports database and Redis status as `ok` or
  `degraded`.

## Getting started

### Prerequisites

- **Docker Desktop** (or Docker Engine + Compose v2). This is all you need for Option A.
- For native development: **Python 3.11**, **Node.js 22**, and a Postgres with
  pgvector plus Redis (Compose can run just those two for you).
- Around **3 GB free disk** for the images. PyTorch (CPU build) and the models make up
  most of it.

### Option A: Docker Compose (recommended)

```bash
git clone https://github.com/Nagesh-max999/pulsesearch.git
cd pulsesearch

cp .env.example .env
# Edit .env and set at least JWT_SECRET to a long random string:
#   openssl rand -hex 32

docker compose up -d --build
```

Compose starts the services in this order:

| Service | What it does | Host port |
|---|---|---|
| `postgres` | `pgvector/pgvector:pg16` | **5433** |
| `redis` | `redis:7-alpine` | **6380** |
| `migrate` | Runs `alembic upgrade head` once, then exits | — |
| `backend` | FastAPI on uvicorn, waits for migrations | **8000** |
| `worker` | arq worker for document processing | **9100** (metrics) |
| `frontend` | Next.js | **3000** |

When it's up:

- App: **http://localhost:3000**
- Interactive API docs (Swagger): **http://localhost:8000/docs**
- Health: http://localhost:8000/api/health
- Metrics: http://localhost:8000/metrics and http://localhost:9100

> **Why ports 5433 and 6380?** They avoid clashing with a Postgres or Redis you may
> already have installed. Containers still talk to each other on the standard 5432/6379
> inside the Docker network. Only tools running *outside* Docker (`psql`, `pytest`, a
> local uvicorn) need the remapped ports.

Useful commands:

```bash
docker compose logs -f backend worker    # follow API + worker logs
docker compose ps                        # service status
docker compose down                      # stop (keeps data)
docker compose down -v                   # stop and delete all data volumes
```

### Option B: Run the backend and frontend natively

**1. Start only the databases**

```bash
docker compose up -d postgres redis
```

**2. Backend**

```bash
cd backend
python -m venv .venv
source .venv/Scripts/activate          # Windows (Git Bash)
# .venv\Scripts\Activate.ps1           # Windows (PowerShell)
# source .venv/bin/activate            # macOS / Linux

pip install --extra-index-url https://download.pytorch.org/whl/cpu -r requirements-dev.txt

cp ../.env.example .env
# In backend/.env, point at the host-mapped ports:
#   DATABASE_URL=postgresql+asyncpg://pulsesearch:pulsesearch@localhost:5433/pulsesearch
#   REDIS_URL=redis://localhost:6380/0
#   UPLOAD_DIR=./uploads

alembic upgrade head                        # create the schema
uvicorn app.main:app --reload               # terminal 1: API on :8000
arq app.workers.worker.WorkerSettings       # terminal 2: background worker
```

The first start downloads the embedding and reranker models (~90 MB each) from Hugging
Face. After that they load from the local cache.

**3. Frontend**

```bash
cd frontend
npm install
cp .env.local.example .env.local            # NEXT_PUBLIC_API_URL=http://localhost:8000
npm run dev                                 # http://localhost:3000
```

### First steps in the app

1. Open http://localhost:3000 and **register**. Three demo documents start processing
   straight away. Watch them on the **Dashboard** or the **Documents** page.
2. **Upload** your own PDF or `.txt`/`.md` file and open it to see the live pipeline
   stepper.
3. Go to **Search** and try the same query in each mode, for example "how does hybrid
   search work". Compare the keyword, semantic and rerank scores on each result.
4. *(Optional)* Enable AI answers in `.env`, restart `backend`, and try the **Ask** page.

## Database schema

```
users ─┬─< documents ──< document_chunks        (content, content_tsv tsvector,
       │        │                                 embedding vector(384), token_count)
       │        └──< processing_jobs            (status, attempt_count, max_attempts,
       │                                          last_error, completed_at)
       ├─< search_events                        (query, mode, result_count, latency_ms)
       └─< password_reset_tokens                (token_hash, expires_at, used_at)
```

Key indexes:

- **GIN** on `document_chunks.content_tsv` for full-text search.
- **IVFFlat** (`vector_cosine_ops`, `lists = 100`) on `document_chunks.embedding` for
  approximate nearest-neighbour search.
- Foreign keys and lookup columns (`users.email`, `documents.user_id`, the reset token
  hash) are indexed.

Every query is **scoped by `user_id`**, so users can only ever see or search their own
documents. Password reset tokens are stored **hashed**, never in plain text.

Migrations live in `backend/alembic/versions/`. The ER diagram and design notes are in
[`docs/database.md`](docs/database.md).

## Observability

- **Prometheus metrics.** The API serves them at `/metrics`: `http_requests_total`,
  `http_request_duration_seconds` and `search_requests_total{mode}`. The worker runs its
  own small metrics server on `:9100` (`documents_processed_total`,
  `embedding_generation_seconds`), because arq has no HTTP server. Scrape both.
- **Request IDs.** The request-ID middleware tags each request and its log lines, which
  makes a single request easy to trace.
- **Structured logging** at `LOG_LEVEL`. Unhandled errors log with an `error_id` that
  is also returned to the client.
- **Health check.** `/api/health` is used by the Docker `HEALTHCHECK`.

## Security

- Passwords are hashed with **bcrypt**. Tokens are JWTs with an expiry.
- **Per-user data isolation** on every query, covered by integration tests for
  cross-user access.
- **Upload validation**: extension allow-list, size limit, and a PDF magic-byte check
  so a renamed file can't pass as a PDF.
- **Password reset**: the response doesn't reveal whether an account exists, tokens are
  hashed, single-use and short-lived, and the endpoint is rate limited.
- **Rate limiting** on search, upload, ask and reset.
- **CORS** is restricted to `CORS_ORIGINS`.
- **Secrets** come only from the environment. `.env` is gitignored, and
  `.env.example` contains placeholders only.
- Search snippets are **sanitized** in the frontend before highlighting.

More detail: [`docs/system-design.md` § 13](docs/system-design.md#13-security).

## Performance

`scripts/benchmark.py` measures real latency against a running instance:

```bash
python scripts/benchmark.py --base-url http://localhost:8000 \
  --requests 200 --concurrency 10 --upload-count 5
```

Latest measured run (non-dedicated Windows host, rate limiting off):

| Metric | p50 | p95 | p99 |
|---|---|---|---|
| Upload → `COMPLETED` (end-to-end) | 563 ms | 1083 ms | 1083 ms |
| Search, 200 req @ concurrency 10, all modes | 116 ms | 1513 ms | 1990 ms |

Cache hits skip Postgres and both models entirely. The tail latency comes from CPU-bound
model inference (embedding plus cross-encoder). `RERANK_ENABLED=false` or a smaller
`RERANK_CANDIDATE_POOL` trades ranking quality for speed. Running this benchmark also
caught **three real concurrency bugs**: model loading blocking the event loop, a
non-single-flight `lru_cache` corrupting the model, and a missing reranker warmup. The
full write-up is in [`docs/performance.md`](docs/performance.md).

## Deployment

Any host that runs Docker Compose works, as does running the two images against managed
Postgres and Redis.

1. **Provision Postgres with the `vector` extension** (the `pgvector/pgvector` image has
   it; on managed services, enable `pgvector`) and **Redis**.
2. **Set production env**: a long random `JWT_SECRET` (`openssl rand -hex 32`), real
   `DATABASE_URL` and `REDIS_URL`, `CORS_ORIGINS` and `FRONTEND_BASE_URL` set to your
   domain, `ENV=production`, SMTP settings for real password-reset emails, and
   `STORAGE_BACKEND=s3` if you run more than one API or worker host.
3. **Build and run**: `docker compose up -d --build`, or push the images to a registry
   and run them behind a reverse proxy or load balancer with TLS.
4. **Frontend**: `NEXT_PUBLIC_API_URL` is baked in at **build time**, so set it to the
   API's public URL and rebuild the frontend image.
5. **Scale**: the API is stateless. Add replicas behind the load balancer, add worker
   replicas for processing throughput, and point `DATABASE_URL_REPLICA` at a read
   replica for search-heavy load.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `port is already allocated` on 5433 / 6380 / 8000 / 3000 | Stop whatever is using the port, or change the left side of the mapping in `docker-compose.yml` |
| First build is slow or large | Expected. PyTorch (CPU) and the embedding model are installed into the image. Later builds use the cache |
| Documents stuck at `UPLOADED` | The worker isn't running or can't reach Redis. Check `docker compose logs worker` |
| Document `FAILED` | Open it to see `error_message`. Common causes are scanned PDFs with no text layer and empty files |
| Search returns nothing for a vague query | That's the reranker's relevance floor working as intended. Try a more specific query, or lower `RERANK_MIN_SCORE` |
| `429 Too Many Requests` | Per-user rate limit. Wait for `Retry-After`, or raise or disable limits in dev |
| `/api/ask` returns `503` | Set `AI_ANSWERS_ENABLED=true` and `ANTHROPIC_API_KEY`, then restart `backend` |
| Frontend can't reach the API / CORS errors | Check that `NEXT_PUBLIC_API_URL` (rebuild the frontend after changing it) and `CORS_ORIGINS` match |
| Native backend can't connect to DB | Use the host ports `localhost:5433` (Postgres) and `localhost:6380` (Redis) |
| Password reset email never arrives | With `SMTP_HOST` empty, the email (and its link) is printed in the backend logs |

## Trade-offs and future work

| Decision | Why | When to revisit |
|---|---|---|
| Local embeddings over a hosted API | Free, offline, private, no external dependency | Higher quality is needed. Switch with `EMBEDDING_PROVIDER=hosted` |
| pgvector over a dedicated vector DB | One database, transactional consistency, simpler ops | Millions of chunks or very high QPS |
| Fixed-window rate limiting | One Redis round trip | A precise burst limit is needed (sliding window or token bucket) |
| Sentence-aware word chunking | Simple and readable, no tokenizer dependency | Token-exact chunking for a specific model |
| SSE over WebSockets | One-way updates, works over plain HTTP | Two-way realtime features |

Full table and future improvements: [`docs/system-design.md` § 15–16](docs/system-design.md#15-trade-offs).
